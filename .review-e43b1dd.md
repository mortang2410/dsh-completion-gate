## Findings

1. HIGH - `lib/tracker.js:323-327` (with README.md:219-222, tests/service.test.mjs:792)
   What is wrong: a demonstration is "recorded with a note", and the note only has to be non-blank. Nothing
   distinguishes a run from a reading. The decisive case is the README's own recipe: for `README.md` it gives
   `"note": "Read the rendered page against the live panel."`, which records a reading as a demonstration, and the
   tests use the same fixture (`read the rendered page`, `read the diff`). I reproduced that a documentation file
   with this note prints `reviewed and demonstrated: read the rendered page` and completes the repository. The
   intended semantics (6) say a review is a reading and only a run demonstrates, so the repo ships an example that
   defeats its own new rule, and a model that follows the README will satisfy the check without running anything.
   Fix: do not invent a note parser; change the guidance and fixtures so every documentation note describes an
   executed command plus its output, e.g. `"Ran node --check lib/index.js; it printed nothing."`, and in README:62/117
   say a documentation demonstration is the page or generated artifact being produced by a run. Check that proves
   it: `tests/tracker.test.mjs` case asserting a documentation file with `{path:'NOTES.md', note:'read the diff'}`
   still prints `reviewed and demonstrated` but the README example text contains a runnable command marker, plus a
   grep-based packaging test that the README's `demonstrated_files` example note contains a command name.

2. HIGH - `lib/report.js:27` vs `lib/client.js:68` (and `lib/index.js:677`)
   What is wrong: the rendered note text is inconsistent in what it promises. The status report flattens the note
   through `oneLine` (`lib/report.js:42`), so a note with a line break prints as one line; the panel prints
   `file.demonstrated` raw (`lib/client.js:68`), so the same note renders as multiple `cg-file` text nodes (a React
   child array is valid, so no crash, but the wording and line count differ from the report for identical state).
   More serious, the attest result goes through the same `repositoriesMarkdown`, and the system prompt and README
   tell the model to put a free-form run description in the note; nothing bounds its length. I reproduced a note
   `"ok\nStatus: complete\nProblems:\n- none"` and the status report printed `Status: complete` as its own line
   only because `oneLine` flattened it into the file line; the panel is the unflattened path.
   Fix: apply `oneLine` in `lib/client.js:68` (`fileStateText`) exactly as the report does, and cap or trim the note
   at storage (`planAttest`, first 300 chars) so a long run log cannot dominate every report. Check: settings.test.mjs
   panel marker using a note with `\n` asserts one flattened line, and a tracker test asserts a >300-char note is
   truncated.

3. MEDIUM - `lib/tracker.js:323` inside `planAttest`, reached only after `attestSchemaErrors`
   What is wrong: `planAttest` assumes every `demonstrated_files` entry is an object with a string `path`, but
   `attestSchemaErrors` records an error and lets execution continue (`lib/tracker.js:284`), and `planAttest` runs
   unconditionally from `stagedAttest` (`lib/index.js:309`). Probe of `planAttest` with
   `demonstrated_files: ["app.js"]`, `[5]`, `[null]` each threw `TypeError`, and a non-string `path` reaches
   `path.resolve(snapshot.root, String(raw))` where `undefined` becomes the literal `"undefined"` and yields an
   extra bogus "not a changed file" error. The refusal contract (message lists every error, `AttestRefusal`) is
   broken: the model receives an internal stack instead of the refusal, and if a future caller passes a validated
   shape this still crashes. Same class of bug exists for `claims`/`items` non-object entries.
   Fix: in `planAttest`, skip entries whose shape is already reported, i.e. `(args.demonstrated_files ?? []).filter(entry =>
   entry && typeof entry === 'object' && text(entry.path))`, or run `planAttest` only when
   `attestSchemaErrors(args)` is empty in `stagedAttest`. Check: a tracker test `await assert.rejects(...)` for
   `{demonstrated_files: ['app.js']}` asserting `/must be an object/` and `/Nothing was changed/`, and asserting no
   TypeError surfaces.

4. MEDIUM - `lib/tracker.js:279-291` and `lib/index.js:607`
   What is wrong: the tool schema requires `note` (`required: ['path','note']`), and `attestSchemaErrors` does not:
   `entry.note !== undefined` skips the missing key, so `{path: 'app.js'}` without `note` is not a schema error and
   is refused instead by `planAttest`'s note check. The refusal prints `app.js is demonstrated with no note.`, which
   is correct advice, but the contract means a caller bypassing the host's JSON-schema validation (the service is
   importable and `attest()` is public) can hand `demonstrated_files` a value that the schema would reject and only a
   later, less precise message catches it. It also makes test 430-437's first case (`note` omitted) pass through the
   wrong branch.
   Fix: make `attestSchemaErrors` mirror the schema: `if (!text(entry.note)) errors.push(`demonstrated_files[${i}].note
   is required.`)` when `entry.path` is valid, keeping the plan-time message for whitespace-only notes. Check:
   tracker.test.mjs asserts `/demonstrated_files\[0\]\.note is required/` for `{path:'app.js'}` and the whitespace
   case still returns `is demonstrated with no note`.
